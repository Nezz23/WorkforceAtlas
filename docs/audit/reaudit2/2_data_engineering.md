# Re-audit 3: Data engineering (independent, read-only)

Score: 7.5/10 (unchanged). Fixes since the last audit are real, but the two new "keep the last file" fallbacks do not work in CI, and the pipeline has still never run (0 commits, no remote).

Checks run: `pytest -q` 48 passed; `actionlint` clean (rc 0); `scripts/check_public.sh web/out` "813 files, nothing private found"; `python -m pipeline.labour` fetched 153 months, 201401 to 202609 (latest 2.3). The web/out build is gitignored; file types are html/txt/js/css/woff2/ico/xml/one pdf, no maps, parquet or csv; the only github.com URL is a core-js license comment.

## Findings

### High
- **H1. The "keep the last file on failure" fallbacks are dead code in CI.** `labour.py:54-61` and `notices.py:~125-133` fall back to `data/published/labour_quits.csv` and `data_notices.json`. `data/published/` is gitignored (.gitignore) and the only thing restored from the `warehouse` release is `data/warehouse` (pipeline.yml:57 `tar -C data warehouse`). A fresh runner never has either file, so the `if not OUT.exists(): raise` branch always fires. A BLS outage, a BLS keyless-API quota hit (v1 is limited to 25 queries per day per IP, and GitHub runner IPs are shared), a non-JSON error page, or an OPM release-notes outage fails the whole run and publishes nothing. The code and the workflow comment ("a change in BLS's API must not block OPM's refresh") promise the opposite. Fix: restore the previous `published-latest` asset in the restore step (`scripts/fetch_data.sh` already exists) before `labour`/`notices`, or include `labour_quits.csv` and `data_notices.json` in the warehouse tarball; add a test that runs `main()` with a failing fetch and a pre-seeded file.
- **H2. Nothing has run end to end** (unchanged from the last audit; `git status`: "No commits yet"). Still unverified: first full rebuild time (docs say "several hours, not measured"), `gh release create` permissions, Playwright in CI, the Cloudflare deploy job, and now the BLS call from a runner IP. Fix: commit to the private repo, `workflow_dispatch` once with `DEPLOY_ENABLED` unset, read the logs.

### Medium
- **M1. A BLS lag across a fiscal-year boundary blocks the whole month.** `models/run.py:41` keeps only fiscal years with 12 quit months, and `exit_model.cells` (exit_model.py:82) keeps only fiscal years with 12 OPM headcount months. If OPM publishes September before BLS publishes the September JOLTS value, FY y is in `df` but not in `quits`; `fit_all` then does `train.fy.map(quits)` (exit_model.py:140) which yields NaN, and `np.average`/GLM fail or poison the fit (the guard at :249 only protects the excess loop, and `run` only checks `if not quits`). `publish` has already written data/published, but the run fails before the release upload, so the month is lost and the issue is a generic "Pipeline failed". Today BLS usually publishes before OPM, so it is a narrow window (September data, once a year), but the failure is silent and ugly. Fix: in `exit_model.run`, drop fiscal years absent from `quits` from `df` (log a warning) instead of mapping NaN; add a test with FY n+1 complete in OPM and 11 months in BLS.
- **M2. `labour.fetch` failure modes are only partly handled.** `main()` catches `OSError` and `RuntimeError`. A `json.JSONDecodeError` (a ValueError, e.g. an HTML error page), a `KeyError` on `d["Results"]["series"][0]` when BLS returns an empty series, or an empty `rates` dict (then `min(rates)` on line 67 raises ValueError and an empty CSV is written first at :63-66) are uncaught. `_open` retries 4 times with 5-40 s sleeps even on 4xx (opm.py:18, HTTPError is an OSError), so a 429 burns the retries. Also the output is not validated: no check that the series is non-empty, monotone in month, or that the latest month is not older than the existing file. Fix: catch `(OSError, ValueError, KeyError, RuntimeError)`, refuse to write fewer months than the previous file, and write via temp + rename (see L2).
- **M3. Quality profile is government-wide only** (carried from the last audit M-D). The DOD Sep 2026 separation collapse is visible only through the hand-reviewed CSV. validate.py:75-82 compares total rows only. Fix: per-department month-on-month ratio band.
- **M4. Notice scoping by regex** (carried M-B). The `departments()` regex still maps "EHRI"/"NASA" to bogus scopes; not re-verified as fixed. Fix: match against the department-code list from the names cube.
- **M5. Release-asset handling is not atomic and has no integrity check.** pipeline.yml:59-61 now uploads `warehouse-next.tar.gz` first, and restore falls back to it (:36-37), which closes last audit's H-A. However: (a) both assets are overwritten with `--clobber` on every run, so a run that fails mid-way (the save step is `always()`) can replace a good `warehouse.tar.gz` with a half-built warehouse (sources.json is written atomically per file, so it is consistent, but the tarball can be taken while `pytest`/publish failed, which is acceptable by design); (b) if the `warehouse` release exists but has neither asset (cancelled during the very first upload), the first `gh release download` fails and so does the fallback, exit 1, and the cron stays red until fixed by hand; (c) neither tarball nor `published.tar.gz` carries a checksum, and `fetch_data.sh` extracts without verifying. Fix: treat "asset not found" like "release not found" (rebuild); publish a `SHA256SUMS` asset and verify in `fetch_data.sh`.
- **M6. Workflow ordering: the public site can lag or lead the data release.** The data release upload (pipeline.yml:78-87) happens after the Playwright run but before "Upload site"; `deploy` needs `refresh` success, so the site deploys only when everything passed, which is correct. But `published-latest` is replaced with `--clobber` and the dated release is created separately, so a failure between line 85 and 87 leaves `latest` ahead of the dated copy. Low impact; fix by uploading the dated asset first.

### Low
- **L1. `scripts/check_public.sh` is a text-pattern scan only.** It would not catch a private repo name, an internal issue URL, or private data that is not credential-shaped. It does correctly exclude maps/parquet/csv/duckdb/env/pem and local paths, and passed on the real build. `api[_-]?key["' ]*[:=]` can false-positive on legitimate copy. Acceptable; consider also failing on `releases/download` and the repo slug.
- **L2. Non-atomic write in `labour.main`** (:63-66) and `notices.main` (:~143): a crash mid-write leaves a truncated CSV that the next run, if the fetch fails, treats as the "last good file". Write to `.tmp` then `rename`.
- **L3. Unpinned `pip-audit` (ci.yml) and `npx --yes wrangler@4.164.0`** is pinned (good) but not integrity-checked; wrangler runs with the Cloudflare token in the same job step. Token is scoped (Pages: Edit) per the comment; fine.
- **L4. `docs/REPRODUCING.md` is mostly reproducible but has gaps.** Option 1 (fetch_data.sh) needs `gh` auth to a private repo and a published release, neither exists yet; it never mentions that `labour_quits.csv` and `data_notices.json` are needed by `models.run`/site and come in the tarball; "several hours, not measured" for a cold build; relative paths in `publish.py` and the exit-model SQL (`read_csv('ref/...')`, exit_model.py:76) still require running from the repo root (carried L-D). The command sequence matches the workflow order (build, notices, labour, publish, models, web).
- **L5. `code_version`/sha256 are still null** in the shipped manifest until a rebuild on a commit (carried).
- **L6. Test coverage gap for new code:** `tests/test_models.py:159` tests only `by_fiscal_year`; nothing covers `labour.fetch` paging, `_open` JSON body, the failure fallback, or `main()`. This is why H1 slipped through.
